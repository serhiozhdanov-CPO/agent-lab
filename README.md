# agent-lab

Песочница для экспериментов с AI-агентами: Claude Code, subagents, MCP-серверы,
hooks, skills и автоматизация разработки.

---

## План тестирования на ближайший месяц

Старт: **26 августа 2026**. Горизонт — 4 недели.

**Цель месяца:** понять, какие агентные сценарии реально экономят время, а какие
создают больше работы, чем убирают. Каждый эксперимент заканчивается записью в
`experiments/` с воспроизводимыми шагами и честным выводом.

**Как меряем.** Для каждого эксперимента фиксируем три вещи:
- *время* — сколько заняло вручную vs. с агентом;
- *качество* — доля результатов, которые ушли в дело без переделки;
- *стоимость* — потраченные токены и число итераций до приемлемого результата.

---

### Неделя 1 (26 авг — 1 сен). База и инфраструктура репозитория

Задача недели — сделать репозиторий пригодным для экспериментов, чтобы дальше
не отвлекаться на обвязку.

- [ ] Каркас проекта: структура каталогов (`experiments/`, `agents/`, `skills/`,
      `scripts/`), выбор языка/рантайма для примеров.
- [ ] `CLAUDE.md` — контекст проекта для агента. Проверить на практике, влияет ли
      он на качество ответов: один и тот же запрос с ним и без него.
- [ ] CI: линтер + тесты на каждый push. Заодно проверить, как агент чинит
      красный CI без подсказок.
- [ ] Шаблон отчёта об эксперименте (`experiments/TEMPLATE.md`): гипотеза,
      постановка, метрики, вывод.
- [ ] SessionStart hook — прогрев окружения (установка зависимостей, прогон
      тестов) перед началом сессии.

**Критерий готовности:** новый эксперимент заводится одной командой, CI зелёный.

---

### Неделя 2 (2 — 8 сен). Subagents и параллельная работа

Задача недели — выяснить, где разделение на несколько агентов даёт выигрыш, а где
это просто трата токенов.

- [ ] Кастомные агенты в `.claude/agents/`: узкоспециализированный ревьюер,
      исследователь кодовой базы, писатель тестов.
- [ ] Fan-out: одна задача разбита на N независимых подзадач и роздана
      параллельно. Замерить wall-clock против последовательного прогона.
- [ ] Сравнение моделей на одной задаче: Opus vs. Sonnet vs. Haiku — где
      разница в качестве оправдывает разницу в цене.
- [ ] Адверсариальная проверка: второй агент пытается опровергнуть находки
      первого. Сколько ложных срабатываний он отсеивает.
- [ ] Антипаттерны: зафиксировать случаи, когда мультиагентность проиграла
      одному агенту в одном контексте.

**Критерий готовности:** таблица «сценарий → один агент или несколько → почему».

---

### Неделя 3 (9 — 15 сен). MCP, инструменты и внешние интеграции

Задача недели — проверить, насколько надёжно агент работает с внешним миром.

- [ ] Свой минимальный MCP-сервер: 2–3 инструмента поверх локальных данных.
- [ ] Готовые серверы: GitHub, Google Drive, файловая система — что работает
      стабильно, что отваливается и как это выглядит со стороны агента.
- [ ] Поведение при ошибках: таймауты, 500-е, битый JSON в ответе инструмента.
      Агент должен деградировать понятно, а не выдумывать результат.
- [ ] Границы прав: проверить, что агент не выходит за разрешённый набор
      инструментов и корректно останавливается на запрете.
- [ ] Prompt injection: подсунуть вредную инструкцию в текст issue, комментария
      и содержимое файла. Зафиксировать, что агент проигнорировал.

**Критерий готовности:** отчёт по надёжности интеграций + список найденных дыр.

### Неделя 4 (16 — 22 сен). Автоматизация реального рабочего процесса

Задача недели — довести один сквозной сценарий до состояния, в котором им можно
пользоваться каждый день.

- [ ] Автоматический code review на PR: качество замечаний, доля шума,
      готовность людей ему доверять.
- [ ] Автофикс красного CI: агент подписан на PR, чинит падения и пушит.
      Считаем, сколько раундов уходит до зелёного.
- [ ] Скиллы: оформить два повторяющихся ритуала (например, разбор логов и
      подготовка релизных заметок) как переиспользуемые skills.
- [ ] Плановые задачи (cron/triggers): ночной прогон и утренняя сводка.
- [ ] Разбор отказов: собрать все случаи, где агент сделал не то, и
      классифицировать причины — плохой промпт, нехватка контекста, ошибка модели.

**Критерий готовности:** один сценарий работает без ручного вмешательства неделю.

## Стенд синтетических данных о здоровье (`synth/`)

Генератор 16 недель суточных записей о здоровье и режиме с заранее заложенными
закономерностями и автоматической проверкой того, что они действительно в данных есть.
Аналитику, которую проверяют на этих данных, можно оценивать объективно: что она обязана
найти, записано заранее и исполняется скриптом.

| Файл | О чём |
|---|---|
| [`expected-patterns.md`](expected-patterns.md) | Двенадцать паттернов: гипотеза, механизм, ожидаемый эффект в числах, критерий обнаружения и то, чем ошибётся наивный анализ |
| [`canonical-format.md`](canonical-format.md) | Формат слоя приёма и восемь решений, которые он фиксирует; контракт адаптера и таблицы маппинга Apple Health, WHOOP и кольца Сбера |
| `synth/` | Канонический слой, контракт адаптера и генератор как первый адаптер |

Зависимостей нет — только Python 3.11 и стандартная библиотека.

```bash
python -m synth.cli --age 38 --weeks 16 --seed 42 --out data/

python tools/validate.py data/synth-0001/observations.jsonl   # соответствие формату
python tools/check_patterns.py data/synth-0001/               # PASS/FAIL по P-01…P-12
```

Один seed даёт побайтово один и тот же файл. Возраст задаётся параметром, и от него
считаются базовые линии пульса покоя, вариабельности, максимального пульса и потребности
во сне. На выходе — поток наблюдений, `manifest.json` и отдельный `ground_truth.json`
с ключом ответов: по нему аналитику можно оценивать, но нельзя, чтобы она в него заглядывала.

Генератор — не самостоятельный скрипт, а **адаптер слоя приёма**: он реализует тот же
контракт (`synth/adapters/base.py`) и пишет тот же формат, что позже будут реализовывать
адаптеры Apple Health, WHOOP и кольца Сбера.

Карточка паттерна в `expected-patterns.md` и код генератора меняются одним коммитом:
`tools/check_patterns.py` исполняет критерии из карточек, поэтому разошедшийся документ
сразу делает проверку красной.
