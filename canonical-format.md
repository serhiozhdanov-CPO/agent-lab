# Канонический формат слоя приёма

Версия схемы: **1.0** · поле `schema_version` в каждой записи

## Место в архитектуре

```
Apple Health ─┐
WHOOP ────────┼─→ адаптер ─→ [ канонический формат ] ─→ хранилище ─→ аналитика
кольцо Сбера ─┤
synth ────────┘
```

Каждый источник данных приходит со своей моделью мира: свои имена метрик, свои единицы, своё
представление о том, к какому дню отнести сон через полночь, своё поведение при отсутствии
данных. Слой приёма существует ровно для того, чтобы эти различия закончились здесь и не
протекли в аналитику.

`synth` — первый адаптер этого слоя и такой же гражданин, как остальные: он реализует тот же
контракт и пишет тот же формат. Отличается он только тем, что источник данных у него не
устройство, а генератор, а значит — известен наперёд.

## Форма: поток наблюдений

**Одна строка JSONL = одно наблюдение.** Файл `observations.jsonl`, кодировка UTF-8,
разделитель строк `\n`, ключи в объекте отсортированы (для побайтовой воспроизводимости).

```json
{
  "schema_version": "1.0",
  "subject_id": "synth-0001",
  "metric": "hrv.rmssd",
  "value": 41.7,
  "unit": "ms",
  "method": "measured",
  "method_detail": "rmssd_night_average",
  "effective_date": "2026-01-19",
  "effective_start": "2026-01-19T01:12:00+03:00",
  "effective_end": "2026-01-19T07:48:00+03:00",
  "timezone": "Europe/Moscow",
  "aggregation": "daily",
  "source": {"vendor": "synthetic", "device": "generator", "adapter_version": "0.1.0"},
  "quality": {"confidence": 0.93, "imputed": false}
}
```

### Поля

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `schema_version` | строка | да | версия этой схемы |
| `subject_id` | строка | да | стабильный идентификатор человека |
| `metric` | строка | да | имя из реестра метрик (ниже) |
| `value` | число | да | значение в канонической единице метрики |
| `unit` | строка | да | каноническая единица; дублирует реестр намеренно, см. решение 2 |
| `method` | enum | да | `measured` · `derived` · `aggregated` · `imputed` (решение 3) |
| `method_detail` | строка | да | окно и алгоритм; вместе с `metric` задаёт сопоставимость |
| `effective_date` | `YYYY-MM-DD` | да | **локальный** день, к которому отнесено наблюдение |
| `effective_start` | ISO 8601 со смещением | нет | начало интервала, если наблюдение интервальное |
| `effective_end` | ISO 8601 со смещением | нет | конец интервала |
| `timezone` | IANA | да | пояс, в котором вычислен `effective_date` |
| `aggregation` | enum | да | `daily` · `point` · `interval` |
| `source.vendor` | строка | да | `apple_health` · `whoop` · `sber_ring` · `synthetic` · `lab` |
| `source.device` | строка | нет | модель устройства или название лаборатории |
| `source.adapter_version` | строка | да | версия адаптера, породившего запись |
| `quality.confidence` | 0..1 | нет | уверенность источника; отсутствует — считать 1.0 |
| `quality.imputed` | bool | да | `true` только если значение восстановлено, а не измерено |

## Восемь решений

Ниже — решения, которые формат фиксирует, и то, почему принято именно так. Они важнее полей:
поля можно добавить, решения при добавлении вендора менять уже поздно.

### 1. Длинный формат, а не широкая суточная таблица

Широкая таблица (строка = день, колонки = метрики) читается глазами и грузится в один вызов,
но каждый новый вендор в ней означает миграцию схемы, а любой вендор приносит что-то своё:
WHOOP — свою метрику нагрузки, кольцо — температуру кожи, Apple Health — десятки типов
за раз. В длинном формате новая метрика — это просто новые строки.

Второе следствие: в широкой таблице отсутствие значения неотличимо от нуля. В потоке
наблюдений отсутствие выражено отсутствием строки — единственным способом (см. решение 5).

Широкая витрина никуда не девается, но она **производная**: её строит потребитель под свою
задачу, а не источник под свою.

### 2. Реестр метрик, у каждой ровно одна каноническая единица

Имена метрик — пространство имён с точкой: `домен.показатель`. Конвертация единиц — обязанность
**адаптера**, не потребителя: если WHOOP отдаёт длительность сна в секундах, а Apple Health —
в минутах, обе записи выходят из слоя приёма в минутах.

Поле `unit` дублирует реестр намеренно. Это делает каждую строку самодостаточной: файл, вынутый
из контекста, остаётся читаемым, а несовпадение `unit` с реестром — сигнал о сломанном адаптере,
который ловит `tools/validate.py`.

#### Реестр 1.0

**Сердечный ритм и вегетатика**

| Метрика | Единица | Агрегация | Смысл |
|---|---|---|---|
| `hr.resting` | `bpm` | daily | пульс покоя за сутки |
| `hr.max_daily` | `bpm` | daily | максимальный пульс за сутки |
| `hrv.rmssd` | `ms` | daily | вариабельность, RMSSD |
| `hrv.sdnn` | `ms` | daily | вариабельность, SDNN — **другая метрика**, не складывать с RMSSD |
| `respiratory.rate` | `brpm` | daily | частота дыхания во сне |

**Сон**

| Метрика | Единица | Агрегация | Смысл |
|---|---|---|---|
| `sleep.duration` | `min` | daily | фактическое время сна |
| `sleep.efficiency` | `pct` | daily | доля сна от времени в постели, 0–100 |
| `sleep.onset` | `min_from_midnight` | daily | момент засыпания, **со знаком** |
| `sleep.offset` | `min_from_midnight` | daily | момент пробуждения |

`min_from_midnight` отсчитывается от полуночи **дня пробуждения**, поэтому значение
отрицательно, если человек уснул до полуночи: `-25` — это 23:35 предыдущего вечера, `+30` —
00:30. Знаковое представление выбрано ради того, чтобы «лёг позже» всегда означало «число
больше» и разность двух отходов ко сну считалась вычитанием, без разбора случаев вокруг полуночи.

**Активность и тело**

| Метрика | Единица | Агрегация | Смысл |
|---|---|---|---|
| `activity.steps` | `count` | daily | шаги |
| `activity.active_energy` | `kcal` | daily | активные килокалории |
| `workout.load` | `au` | daily | тренировочная нагрузка, условные единицы |
| `body.temp_deviation` | `degC` | daily | отклонение ночной температуры от личной базовой линии |
| `body.weight` | `kg` | point | вес, измеряется нерегулярно |

**Самоотчёт**

| Метрика | Единица | Агрегация | Смысл |
|---|---|---|---|
| `context.alcohol_units` | `unit` | daily | условные единицы алкоголя за **вечер этого дня** |
| `subjective.energy` | `score_1_5` | daily | самооценка энергии, 1–5 |

**Лаборатория** (все — `aggregation: "point"`, `source.vendor: "lab"`)

| Метрика | Единица | Метрика | Единица |
|---|---|---|---|

### 3. Метод измерения — условие сопоставимости, а не метаданные «на всякий случай»

Apple Health отдаёт вариабельность как **SDNN** по короткому дневному замеру. WHOOP отдаёт
**RMSSD**, усреднённый по фазе медленного сна. Это разные величины: разная математика, разное
время суток, разная физиология. Числа отличаются в разы, и «средняя вариабельность за неделю»,
посчитанная по смеси этих двух рядов, не значит ничего.

Отсюда два следствия, и оба вшиты в формат.

**`hrv.rmssd` и `hrv.sdnn` — разные метрики реестра**, а не одна метрика от разных источников.
Реестр просто не даёт сложить их в один ряд.

**Каждая запись несёт `method` и `method_detail`.** `method` — одно из `measured` (прибор измерил
напрямую), `derived` (вендор вычислил из своих сырых данных), `aggregated` (свёртка за период),
`imputed` (восстановлено). `method_detail` — строка из фиксированного набора, фиксирующая окно и
алгоритм: `rmssd_night_average`, `sdnn_spot_check_60s`, `night_min_hr`, `sum_local_day`.

Практическое правило:

> Сравнивать **абсолютные значения** можно только внутри одной пары `(metric, method_detail)`.
> Между парами сравнивают динамику, приведённую к персональной базе — отклонение от медианы,
> z-оценку, — но не уровни.

Это не гипотетическая осторожность. Генератор `synth` присылает `hr.resting` двумя способами:
основное устройство пишет `night_min_hr`, кольцо — `ring_night_min_hr`, и уровни у них
расходятся на 1.4 уд/мин просто потому, что окна усреднения разные. Пара `(metric, method_detail)`
делает эту несопоставимость видимой до того, как кто-то усреднит два ряда в один.

`manifest.json` перечисляет для каждой метрики все встретившиеся пары — по нему видно сразу,
где в наборе больше одного способа измерения.

### 4. Правило атрибуции суток

**Сон, пересекающий полночь, относится ко дню пробуждения.** Все метрики, вычисленные по ночному
интервалу — `hrv.rmssd`, `respiratory.rate`, `body.temp_deviation`, `hr.resting` — наследуют этот
же день. Метрики дневной активности относятся к своему календарному дню.

Правило написано явно, потому что вендоры расходятся ровно здесь, и расхождение тихое: оно не
роняет импорт, а просто сдвигает часть ночей на сутки. На недельных сравнениях (P-01) сдвиг
размазывает пятничную ночь между пятницей и субботой и режет амплитуду примерно вдвое.

`effective_date` всегда вычисляется в **локальном** поясе субъекта, записанном в `timezone`.
Хранить UTC-дату и надеяться, что аналитика сама разберётся, нельзя: «во сколько человек лёг»
— вопрос о локальных часах, а не о моменте на оси времени.

### 5. Пропуск — это отсутствие строки

Ни нулей, ни `null`, ни строк-заглушек. Значение либо измерено и записано, либо отсутствует.

Восстановленное значение допустимо, но обязано нести `method: "imputed"` и не имеет права
попасть в слой приёма от адаптера: импутация — решение аналитики, у которой есть задача,
а не адаптера, у которого её нет.

При этом «нет данных» бывает двух разных сортов, и путать их нельзя:

| ситуация | как выглядит | как читать |
|---|---|---|
| источник был, но в этот день не дал значения | строки нет | пропуск; учитывается в покрытии источника |
| источника в этот период ещё не существовало | строк нет **и** день вне `active_from…active_to` этого вендора | не пропуск; ряд источника просто начинается позже |

Различает их не сама запись, а `manifest.json`: он перечисляет для каждого вендора диапазон,
в котором тот вообще присылал данные (решение 8). Кольцо в эталонном наборе подключается
на 56-й день, и покрытие, посчитанное от начала периода, занижает его вдвое.

Известная альтернатива — писать пропуск строкой с `value: null` и полем `missing_reason`.
Она выразительнее: различает «не носил» и «носил, но сигнал не прошёл». Здесь она не выбрана,
и вот почему: нулевое значение в колонке `value` заставляет каждого потребителя проверять
на `null` при каждом чтении, а информация, ради которой это делается, в текущем наборе просто
отсутствует — генератор не моделирует «носил, но не измерилось». Формату не нужна конструкция
под случай, которого в данных нет. Если такой случай появится, решение стоит пересмотреть.

### 6. Редкие и плотные ряды живут в одном потоке

Лабораторный анализ — обычное наблюдение с `aggregation: "point"`. Отдельной сущности для
лабов нет намеренно: как только их выносят в собственную таблицу, соединять их с суточным рядом
приходится каждому потребителю заново, и каждый делает это по-своему. В одном потоке соединение
— это фильтр по `metric`.

Разная частота выражается не структурой, а полем `aggregation` и фактическим набором дат.
`point` означает «замер в момент, значение не относится ко всем суткам»; `daily` — «сводка
за сутки»; `interval` — «величина за явно указанный отрезок `effective_start` … `effective_end`».

### 7. Ключ дедупликации и приоритет источников

Естественный ключ наблюдения:

```
(subject_id, metric, effective_date, source.vendor)
```

Один вендор не имеет права дать два значения одной метрики за один день — это ошибка адаптера,
и `tools/validate.py` считает её нарушением. Разные вендоры — имеют: часы и кольцо оба измеряют
пульс покоя.

Это не теория: генератор `synth` действительно присылает `hr.resting` от двух источников —
основного устройства и кольца (`sber_ring`) — примерно за 45 % дней, причём кольцо
систематически завышает на 1.4 уд/мин. Разница калибровки, а не физиология; на этом стоит
негативный контроль NC2 из `expected-patterns.md`.

Слой приёма такие конфликты **не разрешает**, а сохраняет оба наблюдения. Разрешение — правило
потребителя, и формат лишь даёт ему опору: приоритет по вендору для метрики плюс
`quality.confidence` как тай-брейк. Приоритет по умолчанию для вегетативных метрик:
`whoop` > `sber_ring` > `apple_health`; для шагов — наоборот, телефон видит больше.

### 8. Спутники потока

Рядом с `observations.jsonl` лежат два файла.

**`manifest.json`** — паспорт набора: субъект, возраст, пояс, границы периода, версия генератора
или адаптера, `seed`, диапазоны активности каждого вендора и перечень метрик с покрытием и всеми
встретившимися парами `method:method_detail`. Читается свободно, в том числе аналитикой.

Два поля здесь несут больше, чем кажется. `sources[].active_from` делает вычислимой разницу
между пропуском и «источника ещё не было» (решение 5). `metrics[].methods` показывает, у каких
метрик в наборе больше одного способа измерения, — то есть где нельзя усреднять (решение 3).

```json
{
  "schema_version": "1.0",
  "subject_id": "synth-0001",
  "subject": {"age": 38, "timezone": "Europe/Moscow"},
  "period": {"start": "2026-01-05", "end": "2026-04-26", "days": 112},
  "generator": {"name": "synth", "version": "0.1.0", "seed": 42},
  "sources": [
    {"vendor": "synthetic", "active_from": "2026-01-05", "active_to": "2026-04-26", "active_days": 112},
    {"vendor": "sber_ring", "active_from": "2026-03-04", "active_to": "2026-04-26", "active_days": 54}
  ],
  "metrics": [{"metric": "hr.resting", "unit": "bpm", "count": 101, "coverage": 0.902,
               "methods": ["measured:night_min_hr", "measured:ring_night_min_hr"]}]
}
```

**`ground_truth.json`** — ключ ответов: журнал заложенных событий и экземпляров паттернов,
с ID из `expected-patterns.md`.

```json
{
  "patterns": [
    {"id": "P-04", "name": "Окно острой болезни",
     "instances": [{"acute_days": [62, 63, 64, 65], "peak_day": 63, "peak_hr_delta": 12.0}]}
  ]
}
```

Он вынесен отдельным файлом сознательно: аналитику по нему можно **оценивать**, но нельзя, чтобы
она в него **заглядывала**. Файл не является частью канонического формата — это метаданные стенда.
У реальных адаптеров его нет и быть не может.

## Контракт адаптера

Каждый источник реализует один и тот же протокол (`synth/adapters/base.py`):

```python
class Adapter(Protocol):
    name: str              # "synthetic", "apple_health", "whoop", "sber_ring"
    adapter_version: str

    def capabilities(self) -> set[str]:
        """Метрики реестра, которые этот источник в принципе умеет отдавать."""

    def read(self, raw: Any) -> Iterator[Observation]:
        """Разобрать сырьё источника в поток канонических наблюдений."""
```

Обязанности адаптера, и только его:

1. привести имена к реестру метрик и значения — к каноническим единицам;
2. проставить `method` и `method_detail`: без них значение попадёт в чужой ряд;
2. вычислить `effective_date` в локальном поясе субъекта по правилу атрибуции суток;
4. **не** заполнять пропуски — отсутствующее данное просто не порождает строки;
5. проставить `source` и, если источник её сообщает, `quality.confidence`;
6. заявить в `capabilities()` только то, что действительно умеет, — набор метрик
   `hrv.rmssd` у кольца и у часов может отличаться, и потребителю нужно это знать заранее.

Чего адаптер делать не должен: сглаживать, усреднять по неделям, отбрасывать выбросы,
разрешать конфликты между вендорами. Всё это — решения с потерей информации, и принимать их
на слое приёма означает принимать их за всех потребителей сразу.

## Что каждый адаптер обязан отобразить

Таблицы ниже фиксируют целевой контракт: во что превращается поле источника и с каким
`method_detail`. Адаптеры ещё не написаны — таблицы существуют затем, чтобы их писали под
уже принятые решения, а не наоборот.

### Apple Health

Источник: XML-экспорт `export.xml` или HealthKit напрямую. `source.vendor: "apple_health"`.

| идентификатор HealthKit | метрика | method | method_detail |
|---|---|---|---|
| `HKQuantityTypeIdentifierHeartRateVariabilitySDNN` | `hrv.sdnn` | `measured` | `sdnn_spot_check_60s` |
| `HKQuantityTypeIdentifierRestingHeartRate` | `hr.resting` | `derived` | `apple_daily_resting_estimate` |
| `HKQuantityTypeIdentifierStepCount` | `activity.steps` | `aggregated` | `sum_local_day` |
| `HKQuantityTypeIdentifierActiveEnergyBurned` | `activity.active_energy` | `aggregated` | `sum_local_day` |
| `HKCategoryTypeIdentifierSleepAnalysis` | `sleep.*` | `aggregated` | `apple_sleep_stages_merged` |
| `HKQuantityTypeIdentifierBodyMass` | `body.weight` | `measured` | `scale_sync` |

Что адаптер обязан учесть:

- Apple отдаёт **SDNN, а не RMSSD**. Это `hrv.sdnn`, и складывать её с рядом WHOOP нельзя
  (решение 3). Метрики `hrv.rmssd` у Apple Health просто нет.
- Один интервал приходит **несколькими перекрывающимися сэмплами** от разных устройств —
  часы, телефон, сторонние приложения. Дедупликация по имени источника и интервалу, приоритет
  у часов. Наивная сумма даёт двойной счёт шагов.
- Шаги идут с телефона и переживают разряд часов, поэтому в наборе бывают дни, где
  `activity.steps` есть, а ночных метрик нет. Это не повод считать день пропущенным целиком.

### WHOOP

Источник: WHOOP API. `source.vendor: "whoop"`.

| поле API | метрика | преобразование | method | method_detail |
|---|---|---|---|---|
| `recovery.score.hrv_rmssd_milli` | `hrv.rmssd` | → мс | `measured` | `rmssd_slow_wave_sleep_5min` |
| `recovery.score.resting_heart_rate` | `hr.resting` | как есть | `measured` | `whoop_sleep_min_hr` |
| `recovery.score.skin_temp_celsius` | `body.temp_deviation` | минус персональная база | `derived` | `deviation_from_30d_baseline` |
| `sleep.start` / `sleep.end` | `sleep.onset` / `sleep.offset` | → минуты от локальной полуночи | `measured` | `whoop_sleep_boundaries` |
| `sleep.score.sleep_efficiency_percentage` | `sleep.efficiency` | как есть | `derived` | `whoop_efficiency` |
| `cycle.score.strain` | `workout.load` | шкала не совпадает | `derived` | `whoop_strain_v2` |

Что адаптер обязан учесть:

- Поле с именем `..._milli` в части версий API приходит **в микросекундах**. Адаптер обязан
  проверять порядок величины и падать с внятной ошибкой, а не молча делить на тысячу.
- WHOOP различает основной и дневной сон. В `sleep.*` идёт только основной.
- Ночь у WHOOP привязана к «циклу», граница цикла может не совпадать с локальной полуночью.
  Правило атрибуции суток (решение 4) имеет приоритет над границей цикла.
- `strain` — не то же самое, что тренировочная нагрузка в условных единицах реестра. Шкала
  приводится на этапе адаптера, исходная фиксируется в `method_detail`.

### Кольцо Сбера

`source.vendor: "sber_ring"`. **Таблица — заглушка**: поля API уточняются при подключении.
Зафиксированы целевые метрики и `method_detail`, чтобы адаптер писался под готовый контракт.

| метрика | method | method_detail | что уточнить |
|---|---|---|---|
| `hrv.rmssd` | `measured` | `ring_rmssd_night_average` | окно усреднения |
| `hr.resting` | `measured` | `ring_night_min_hr` | минимум за ночь или среднее |
| `sleep.*` | `measured` | `ring_sleep_stages` | состав фаз |
| `respiratory.rate` | `measured` | `ring_night_average` | — |
| `activity.steps` | `aggregated` | `sum_local_day` | пересекается с Apple Health, нужен приоритет |

Что известно заранее:

- **Систематическое смещение относительно наручного трекера.** Кольцо и часы меряют в разных
  местах и усредняют по разным окнам; на одном человеке ряды расходятся на устойчивую величину.
  Смещение оценивается на окне параллельного ношения и попадает в отчёт, но значения в
  хранилище **не корректируются** — обе строки лежат как есть (решение 7).
- **Ряд начинается в середине наблюдения.** Дней до первой синхронизации быть не должно:
  не строки-заглушки, а отсутствие строк плюс `active_from` в манифесте (решения 5 и 8).

## Версионирование формата

`schema_version` растёт по semver, и правило простое.

**Ломающие изменения (major):** удаление или переименование поля; смена канонической единицы
у существующей метрики; смена семантики — например, атрибуция сна с дня пробуждения на день
засыпания; удаление значения из перечисления.

**Совместимые (minor):** новая метрика в реестре; новое значение в перечислении `method` или
новый вендор; новое необязательное поле.

Читатели обязаны **игнорировать незнакомые поля** и **падать на незнакомой major-версии**.
Молча проглотить чужую major-версию хуже, чем остановиться: тихо разъехавшаяся семантика
обнаруживается через недели, и к тому моменту в хранилище уже лежит смесь двух форматов.

## Валидация

`tools/validate.py` проверяет поток на:

- обязательные поля и их типы;
- `metric` из реестра и совпадение `unit` с канонической единицей метрики;
- `method` из допустимого набора и непустой `method_detail`: без него значение не с чем
  сравнивать;
- допустимость `aggregation` для метрики;
- корректность дат и согласованность `effective_start ≤ effective_end`;
- отсутствие дублей по ключу `(subject_id, metric, effective_date, vendor)`;
- значения в физически возможных границах реестра;
- отсутствие `null` в `value`.
