# Контракт отчёта аналитики

`schema_version: 1.0`

Отчёт — один файл `report.json` в корне рабочего каталога. Только этот файл
читает оценщик; всё остальное, что вы напишете рядом, он игнорирует.

Все даты — `YYYY-MM-DD`. Все числа — числа, не строки. Незаполненный раздел —
пустой список, а не отсутствующее поле и не `null`.

---

## Верхний уровень

```json
{
  "schema_version": "1.0",
  "baselines": {},
  "events": [],
  "couplings": [],
  "trends": [],
  "missingness": {},
  "source_divergence": []
}
```

---

## `baselines`

Персональные базовые линии по спокойной части периода. Ключ — канонический
идентификатор метрики из словаря в `data-format.md`.

```json
"baselines": {
  "hr_resting": {"median": 0.0, "iqr": [0.0, 0.0], "unit": "bpm"},
  "hrv_rmssd":  {"median": 0.0, "iqr": [0.0, 0.0], "unit": "ms"}
}
```

Обязательно поле `median`. `iqr` и `unit` желательны.

---

## `events`

Периоды, когда происходило что-то заметное. Одно событие — один объект.

```json
"events": [
  {
    "id": "e1",
    "kind": "timezone_shift",
    "from": "2026-01-01",
    "to": "2026-01-05",
    "confidence": 0.8,
    "evidence": "одной фразой: по каким признакам"
  }
]
```

| Поле | Обязательно | Что |
|---|---|---|
| `id` | да | ваш идентификатор, любой уникальный в пределах отчёта |
| `kind` | да | вид события из перечня ниже |
| `from`, `to` | да | границы **основной фазы** события, без хвоста восстановления |
| `confidence` | нет | 0..1; на баллы не влияет, нужна для разбора расхождений |
| `evidence` | нет | одна фраза, по каким признакам |

Перечень `kind`:

| Значение | Что означает |
|---|---|
| `timezone_shift` | смещение суточного ритма из-за смены часового пояса |
| `regimen_collapse` | человек сам сломал себе режим |
| `illness` | острое состояние с признаками болезни |
| `training_block` | период повышенной тренировочной нагрузки |
| `other` | что-то ещё; в зачёт по видам не идёт, но и не штрафуется как выдумка, если попало в реальное окно |

Границы: событие засчитывается, если его вид совпал и окно пересекается с
эталонным не меньше чем на треть по IoU. Хвост восстановления в эталонное окно
не входит, но и не считается ошибкой — если ваш `to` заехал в хвост, IoU это
переживёт.

---

## `couplings`

Связи «одна метрика влияет на другую».

```json
"couplings": [
  {
    "cause": "sleep_onset",
    "effect": "hrv_rmssd",
    "lag_days": 1,
    "effect_size": 0.0,
    "unit": "pct_per_hour_late"
  }
]
```

| Поле | Обязательно | Что |
|---|---|---|
| `cause`, `effect` | да | канонические идентификаторы метрик |
| `lag_days` | да | сдвиг в сутках: 0 — в тот же день, 1 — на следующий |
| `effect_size` | да | величина эффекта, со знаком |
| `unit` | да | единица из перечня ниже |

Перечень `unit`:

| Значение | Что означает |
|---|---|
| `pct_per_hour_late` | процент изменения на каждый час более позднего отбоя |
| `ms_per_hour_late` | миллисекунд изменения на каждый час более позднего отбоя |
| `bpm_per_hour_late` | ударов в минуту на каждый час более позднего отбоя |

Оценщик умеет переводить `pct_per_hour_late` в `ms_per_hour_late` и обратно
через вашу же базовую линию, так что выбор единицы на баллы не влияет —
влияет её честное указание.

**Связь, которой в данных нет, штрафуется.** Заявленная зависимость между
метриками, между которыми в действительности нет механизма, снимает балл так
же, как пропущенная настоящая.

---

## `trends`

Медленные изменения на горизонте всего периода.

```json
"trends": [
  {
    "metric": "hr_resting",
    "source": "sber_ring",
    "verdict": "real",
    "total_change": 0.0,
    "unit": "bpm",
    "cause": "одной фразой"
  }
]
```

| Поле | Обязательно | Что |
|---|---|---|
| `metric` | да | канонический идентификатор метрики |
| `source` | нет | источник, если тренд привязан к конкретному источнику |
| `verdict` | да | `real` — изменение в человеке; `artifact` — следствие того, как собирались данные |
| `total_change` | нет | изменение за весь период, со знаком |
| `unit` | нет | единица `total_change` |
| `cause` | нет | одной фразой, чем вызвано |

Главное здесь — `verdict`. Тренд, найденный правильно, но объявленный
физиологией вместо артефакта сбора, засчитывается как ошибка.

---

## `missingness`

```json
"missingness": {
  "mechanism": "MNAR",
  "gaps": [{"from": "2026-01-01", "to": "2026-01-03", "reason": "battery"}],
  "imputed": false
}
```

| Поле | Обязательно | Что |
|---|---|---|
| `mechanism` | да | `MCAR` — пропуски случайны; `MAR` — зависят от наблюдаемого; `MNAR` — зависят от того, что как раз и пропущено |
| `gaps` | да | список окон без данных; `reason` необязателен |
| `imputed` | да | заполняли ли вы пропуски. Заполнение само по себе не ошибка — ошибка не сказать об этом |

---

## `source_divergence`

Расхождения между источниками, меряющими одно и то же.

```json
"source_divergence": [
  {
    "source_a": "whoop",
    "source_b": "sber_ring",
    "metric": "hrv_rmssd",
    "kind": "multiplicative",
    "effect": 1.0,
    "verdict": "instrumental"
  }
]
```

| Поле | Обязательно | Что |
|---|---|---|
| `source_a`, `source_b` | да | идентификаторы источников; порядок значения не имеет |
| `metric` | да | по какой метрике расхождение |
| `kind` | да | `additive` — постоянная добавка; `multiplicative` — постоянный множитель |
| `effect` | да | величина: добавка в единицах метрики или множитель |
| `verdict` | нет | `instrumental` — разница приборов; `physiological` — разница в человеке |

Для `additive` эффект указывается как «`source_a` минус `source_b`», для
`multiplicative` — как «`source_a` делить на `source_b`». Если вы посчитали в
обратную сторону, оценщик это распознает и не штрафует.
