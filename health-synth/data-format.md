# Единый формат записи данных о здоровье и режиме

`schema_version: 1.0`

Один контракт, в который пишут все источники: генератор синтетики, адаптер Apple Health,
адаптер WHOOP, адаптер кольца Сбера, ручной ввод лабораторных результатов.

Базовое правило: **одна строка — одно наблюдение** (long format). Не «день со всеми
метриками в колонках», а именно длинная таблица. Так новый источник или новая метрика
добавляются без изменения схемы, а разные источники не дерутся за одну ячейку.

---

## 1. Схема полей

### Обязательный минимум

| Поле | Тип | Описание |
|---|---|---|
| `date` | `YYYY-MM-DD` | Локальная дата человека, к которой относится наблюдение. Для ночных метрик — дата **пробуждения** (сон в ночь с 25-го на 26-е записывается на 26-е). |
| `metric` | enum | Канонический идентификатор показателя (раздел 2). |
| `value` | number | Значение. Всегда число, никогда строка. |
| `unit` | enum | Единица измерения (раздел 2). Дублирует метрику намеренно: строка должна читаться в отрыве от словаря. |
| `source` | enum | `sber_ring` \| `apple_health` \| `whoop` \| `lab` \| `synthetic` |
| `method` | enum | Как получено значение (раздел 1.2). |

### Служебные поля

Без них адаптеры не соберутся — каждое объяснено ниже.

| Поле | Тип | Зачем |
|---|---|---|
| `record_id` | hex-16 | Детерминированный хеш `date\|metric\|source`. Ключ идемпотентности: Apple Health при повторном экспорте отдаёт те же сэмплы заново, и без такого ключа хранилище получит дубли. |
| `period_start` | ISO-8601 с офсетом | Начало интервала измерения. |
| `period_end` | ISO-8601 с офсетом | Конец интервала. Apple Health пишет интервальные сэмплы, WHOOP — сессии сна с реальными таймстампами; голой даты им не хватает. Для точечных метрик `period_start == period_end`. |
| `tz_offset` | `±HH:MM` | Часовой пояс на момент измерения. **Ключевое поле датасета:** без него смена часового пояса в командировке неотличима от срыва режима. |
| `quality` | enum | `ok` \| `low_confidence` \| `estimated` |
| `source_version` | string | Версия прошивки или приложения (`sber_ring/2.4.1`, `whoop/4.9.2`, `ios/18.3`). Нужна, чтобы объяснить скачок в данных сменой алгоритма источника. |
| `original_metric` | string | Собственное имя поля у источника: `HKQuantityTypeIdentifierRestingHeartRate`, `whoop.recovery.hrv_rmssd_milli`. Провенанс для отладки адаптера. |
| `ingested_at` | ISO-8601 UTC | Когда строка попала в хранилище. Отличается от `period_start`: лаборатория отдаёт результат через 2–3 дня после забора. |

### 1.1. Пример строки

CSV:

```csv
record_id,date,metric,value,unit,source,method,period_start,period_end,tz_offset,quality,source_version,original_metric,ingested_at
a3f19c2b8e04d7f1,2026-03-27,hrv_rmssd,28,ms,sber_ring,device_measured,2026-03-27T02:10:00+03:00,2026-03-27T09:05:00+03:00,+03:00,ok,sber_ring/2.4.1,sber.sleep.hrv_rmssd_ms,2026-03-27T09:31:00Z
```

JSONL:

```json
{"record_id":"a3f19c2b8e04d7f1","date":"2026-03-27","metric":"hrv_rmssd","value":28,"unit":"ms","source":"sber_ring","method":"device_measured","period_start":"2026-03-27T02:10:00+03:00","period_end":"2026-03-27T09:05:00+03:00","tz_offset":"+03:00","quality":"ok","source_version":"sber_ring/2.4.1","original_metric":"sber.sleep.hrv_rmssd_ms","ingested_at":"2026-03-27T09:31:00Z"}
```

Оба представления содержат ровно одно и то же. CSV — чтобы открыть глазами и в Excel,
JSONL — чтобы адаптеры дописывали строки потоком.

Живой пример формата целиком — `sample-run/records.csv` и `sample-run/records.jsonl`:
1661 запись от четырёх источников за 16 недель, включая дни, где на одну дату
приходится по три разных значения одной метрики.

### 1.2. Словарь `method`

| Значение | Смысл | Пример |
|---|---|---|
| `device_measured` | Прибор измерил физически | пульс с оптического датчика кольца |
| `device_derived` | Прибор посчитал из измеренного по своему алгоритму | фазы сна, `activity_load` |
| `app_aggregated` | Приложение свело данные из нескольких сэмплов или источников | суточные шаги в Apple Health |
| `manual_entry` | Человек ввёл руками | вес, самочувствие |
| `lab_assay` | Лабораторный анализ | hs-CRP |
| `imputed` | Значение восстановлено алгоритмом, а не измерено | заполнение пропуска |

`method` — не украшение. Он отвечает на вопрос «насколько этому числу можно верить»
и разделяет измеренное от посчитанного. `device_derived` и `imputed` в анализе тренда
обязаны иметь меньший вес, чем `device_measured`.

## 2. Словарь метрик

Диапазон — физиологически правдоподобные границы; значения за их пределами считаются
браком адаптера, а не редким случаем.

### Ночные / восстановление

| `metric` | `unit` | Диапазон | Направление |
|---|---|---|---|
| `hr_resting` | `bpm` | 35–100 | меньше = лучше |
| `hrv_rmssd` | `ms` | 8–150 | больше = лучше |
| `respiratory_rate` | `brpm` | 10–22 | стабильность = лучше |
| `body_temp_delta` | `C` | −1.5…+2.0 | отклонение от личной нормы |

### Сон

| `metric` | `unit` | Диапазон | Направление |
|---|---|---|---|
| `sleep_duration` | `min` | 0–900 | ближе к личной норме = лучше |
| `sleep_onset` | `min` | −300…+360 | раньше и стабильнее = лучше |
| `sleep_efficiency` | `pct` | 40–100 | больше = лучше |
| `sleep_deep` | `min` | 0–240 | больше = лучше |
| `sleep_rem` | `min` | 0–240 | больше = лучше |

**`sleep_onset` кодируется как минуты от локальной полуночи со знаком:** `−45` = 23:15,
`0` = 00:00, `+90` = 01:30. Иначе полночь рвёт любое усреднение: среднее между 23:50 и
00:10 в формате «часы:минуты» даёт 11:59 дня вместо полуночи. Со знаковыми минутами
среднее между `−10` и `+10` честно равно `0`.

### Активность

| `metric` | `unit` | Диапазон | Направление |
|---|---|---|---|
| `steps` | `count` | 0–40000 | контекстно |
| `active_energy` | `kcal` | 0–3000 | контекстно |
| `activity_load` | `score` | 0–21 | контекстно (нужен и отдых, и нагрузка) |

### Покрытие данных

| `metric` | `unit` | Диапазон | Направление |
|---|---|---|---|
| `wear_hours` | `h` | 0–24 | больше = надёжнее остальные метрики этого дня |

`wear_hours` — служебная метрика, но она полноправная строка в тех же данных. Она одна
позволяет отличить «человек не носил устройство» от «данных нет вообще» (см. раздел 4).

### Лабораторные

| `metric` | `unit` | Диапазон | Направление |
|---|---|---|---|
| `hs_crp` | `mg/L` | 0.1–20 | меньше = лучше |
| `ferritin` | `ng/mL` | 5–400 | коридор |
| `vitamin_d_25oh` | `ng/mL` | 5–100 | коридор |
| `hba1c` | `pct` | 4.0–9.0 | меньше = лучше |
| `tsh` | `mIU/L` | 0.3–6.0 | коридор |
| `cortisol_morning` | `nmol/L` | 100–800 | коридор |

## 3. Маппинг источников

Что именно каждый адаптер должен превратить в канонические метрики. Пустая ячейка — источник
такую метрику не отдаёт; заполнять её вычислением из соседних **нельзя** (это был бы
`device_derived` с чужой ответственностью).

| Каноническая метрика | Apple Health | WHOOP | Кольцо Сбера |
|---|---|---|---|
| `hr_resting` | `HKQuantityTypeIdentifierRestingHeartRate` | `recovery.resting_heart_rate` | `sber.sleep.hr_resting_bpm` |
| `hrv_rmssd` | `HKQuantityTypeIdentifierHeartRateVariabilitySDNN` ⚠️ | `recovery.hrv_rmssd_milli` | `sber.sleep.hrv_rmssd_ms` |
| `sleep_duration` | `HKCategoryValueSleepAnalysisAsleep*` (сумма) | `sleep.score.stage_summary.total_in_bed_time_milli` минус wake | `sber.sleep.total_min` |
| `sleep_onset` | первый `asleep`-сэмпл сессии | `sleep.start` | `sber.sleep.onset_local` |
| `sleep_efficiency` | — | `sleep.score.sleep_efficiency_percentage` | `sber.sleep.efficiency_pct` |
| `sleep_deep` | `HKCategoryValueSleepAnalysisAsleepDeep` | `stage_summary.total_slow_wave_sleep_time_milli` | `sber.sleep.deep_min` |
| `sleep_rem` | `HKCategoryValueSleepAnalysisAsleepREM` | `stage_summary.total_rem_sleep_time_milli` | `sber.sleep.rem_min` |
| `respiratory_rate` | `HKQuantityTypeIdentifierRespiratoryRate` | `sleep.score.respiratory_rate` | `sber.sleep.resp_rate_brpm` |
| `body_temp_delta` | `HKQuantityTypeIdentifierAppleSleepingWristTemperature` | `recovery.skin_temp_celsius` (абсолютная) | `sber.sleep.temp_delta_c` |
| `steps` | `HKQuantityTypeIdentifierStepCount` | — | `sber.activity.steps` |
| `active_energy` | `HKQuantityTypeIdentifierActiveEnergyBurned` | `cycle.score.kilojoule` | — |
| `activity_load` | — | `cycle.score.strain` | `sber.activity.load_score` |
| `wear_hours` | — | `cycle.wearable_uptime` | `sber.device.wear_hours` |

### Ловушки адаптеров, которые обязаны быть учтены

⚠️ **Apple Health отдаёт SDNN, а не RMSSD.** Это разные метрики вариабельности, их нельзя
писать в `hrv_rmssd` как есть. Либо адаптер конвертирует и ставит `method: device_derived`
и `quality: estimated`, либо заводится отдельная метрика `hrv_sdnn`. Молча подменять —
худший вариант: анализ получит скачок на границе источников и примет его за физиологию.

**Единицы.** WHOOP отдаёт миллисекунды для длительностей сна и килоджоули для энергии.
Конвертация — работа адаптера, в хранилище попадают только канонические единицы из раздела 2.

**Абсолютное против дельты.** WHOOP пишет абсолютную температуру кожи, Apple и кольцо —
отклонение от личной базы. Адаптер WHOOP обязан вычесть свою базу, иначе `body_temp_delta`
станет смесью двух разных величин.

**Apple Health как зеркало.** iOS-приложение WHOOP пишет свои данные обратно в Apple Health.
Строка приезжает во второй раз, уже с `source: apple_health`. Это не дубль по `record_id`
(`source` разный) — и это реальный источник двойного учёта. Адаптер Apple Health обязан
проверять поле происхождения сэмпла и ставить `quality: low_confidence` для чужих данных.

**Ночь через полночь.** `date` для ночных метрик — дата пробуждения. Три источника режут
сутки по-разному; правило одно на всех и живёт здесь, а не в каждом адаптере.

## 4. Пропуски

**Пропуск — это отсутствие строки, а не строка с `null`.** `value` всегда число.

Чтобы отличить причины пропуска, читаем `wear_hours` за тот же день:

| Что видно в данных | Как читать |
|---|---|
| Нет строк метрики, есть `wear_hours` с низким значением (0–6) | Устройство было, но не надето — данных нет по поведению человека |
| Нет строк метрики и нет `wear_hours` | Устройство молчало — разряд, потеря, сбой синхронизации |
| Есть `wear_hours` ≈ 24, но нет метрик сна | Носил, но не спал или сон не распознан |
| Строки есть, `quality: low_confidence` | Данные есть, доверять им нужно меньше |

Это различие обязательно: пропуски бывают **неслучайными**. Человек перестаёт носить кольцо
именно в те дни, когда режим сорван, — и наивное «выбросим дни без данных» систематически
занижает глубину провала. Аналитика обязана проверять, случайны ли пропуски, а формат обязан
дать ей для этого материал.

## 5. Конфликты источников

Два источника дают `hr_resting` на одну дату — нормальная ситуация в период, когда человек
носит и кольцо, и WHOOP.

**Правило записи: сохраняются обе строки.** `record_id` у них разный, потому что разный
`source`. Никакого разрешения конфликта на уровне записи не происходит.

Причина: расхождение источников — это данные, а не мусор. Систематическая разница между
кольцом и WHOOP в 6% по HRV — сама по себе находка, и она нужна, чтобы понять, можно ли
склеивать два периода в один тренд. Если слой записи выберет «правильное» значение и
выбросит второе, эта информация исчезнет навсегда.

**Разрешение живёт в слое аналитики** — как view поверх данных, по таблице приоритетов:

| Метрика | Приоритет | Почему |
|---|---|---|
| `hr_resting`, `hrv_rmssd` | `sber_ring` → `whoop` → `apple_health` | Кольцо на пальце меряет ночью надёжнее наручного; Apple отдаёт SDNN |
| `sleep_*` | `whoop` → `sber_ring` → `apple_health` | У WHOOP лучшее стадирование сна |
| `steps`, `active_energy` | `apple_health` → `sber_ring` | Телефон почти всегда с человеком |
| `activity_load` | `whoop` → `sber_ring` | Разные шкалы, смешивать нельзя |
| лабораторные | `lab` | Единственный источник |

Два требования к любому такому view:

1. **Не смешивать источники внутри одного тренда без поправки на смещение.** Переход с
   кольца на WHOOP посреди графика HRV даёт ступеньку, которая выглядит как физиология,
   но ею не является. Либо считать смещение на перекрывающемся периоде и вычесть его, либо
   строить тренды по источникам раздельно.
2. **Не суммировать перекрывающиеся источники.** Шаги с телефона и шаги с кольца за один
   день — это одни и те же шаги, а не удвоенная активность.

## 6. Версионирование формата

`schema_version` растёт по semver.

**Ломающие изменения (major):** удаление или переименование поля; смена единицы измерения
у существующей метрики; смена семантики (например, `date` с даты пробуждения на дату засыпания);
удаление значения из enum.

**Совместимые (minor):** новая метрика в словаре; новое значение в enum `source` или `method`;
новое необязательное поле.

Читатели обязаны игнорировать незнакомые поля и падать на незнакомом major — молча
проглотить чужую major-версию хуже, чем остановиться.
